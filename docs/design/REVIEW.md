# 実装面レビュー — v2→v3→v3.2

対象：DOT_MIC_V2_DESIGN_AND_PROMPTS.mdおよび同梱パック。ソースリポジトリや完成アプリは提示されていないため、実コードの不具合レビュー／性能測定ではない。以下は設計・実装指示のレビューである。


## v3.2で追加した変更
- エージェント運用をモデル別に修正した。**Astraでは従来どおり主エージェント単独とし、サブエージェント・並列エージェント・別レビューエージェントを使用しない。Astra以外ではこれらの制限を無効化する。** この方針はDOT MIC固有ではなく、利用者の全プロジェクト共通として明文化した。
- Astra以外で複数writerを使う場合も、別worktree／branchまたは非重複ファイル範囲を使い、統合責任を一つに保つ。同一作業ツリーの競合回避はエージェント数の制限ではなく、実装整合性を守る運用原則である。
- E4最適化後に最終Release candidateをfreezeし、E5では原則として同一バイナリをpackageする。性能測定対象と配布バイナリが別物になる問題を解消した。
- clean buildは毎回の必須工程ではなく、必要な場合の再現性確認に限定した。clean build成果へ差し替える場合のみ新RCとして影響範囲を再確認する。

## 結論
v2の音声中核は概ね必要である。過剰なのは、同じ要件の重複管理、全試験の一律リリース必須化、定数の総当たり、検証資料を揃えるための追加工程である。音声経路を危うくして短縮するより、作るものと調べるものを増やさない方が有効である。実装時間の削減率は未実装のため算出しない。

v2には47ファイル（manifestを含む）、11本の工程等プロンプト、8工程、56項目の必須試験定義がある。v3は9ファイル、主プロンプト1本、5つの連続した作業ブロック、2つの検証入口へ再編する。本数を減らしただけで同等の試験網羅性を保証するものではなく、低頻度・多機種条件の必須実測を明示的に外している。

## 残す対策と理由
**独立dry＋3本SPSC**は残す。推論するworker自身にdry供給も任せると、Runが戻らない間に原音も途切れる。dry/jobs/wetは小さい固定長queueで足り、ここを2本に戻すことは有効な工程削減ではない。

**モデルの正しい初期状態・前後処理と短い参照比較**は残す。公式実装は960/480、複素スペクトル、metadata由来のnorm初期値を使う。全ゼロstateやPCMをそのままモデルへ渡す誤りは見た目だけでは判別しにくい。短い一つのgolden fixtureで確認する価値がある。[S04][S05]

**時間整合・OFF停止・ゲート・ゲイン平滑化・最終limiter・clock補正・端点復旧**は製品動作そのものであり、テスト削減のために省かない。NC停止とアプリ全体停止、NCが原音へ退避した状態と正常ONを区別する。

**stop→rebuild→start**は既にv2の妥当な選択である。ここをライブ差し替えや世代資源の複雑な回収へ変えない。generationは旧NC結果の混入を防ぐ小さな識別子として残す。汎用の分散状態管理は不要。

**モデルhash、依存lock、license、安全なDLL読み込み**は簡単な配布品質管理として残す。モデルhashは取得時／配布時／初回ロードで足り、毎hopや毎トグルで再確認しない。依存lockと同じ内容の独自台帳を重ねない。

## 実装を単純にする具体策
入力Trimは0dBなので乗算専用のstageを作らない。gate/gainのpowや閾値logは設定変更時に計算し、サンプル処理では使い回す。NC切替専用のgateモードは原則作らず、検出envelopeを保持した通常処理で扱う。切替で語頭が欠ける問題が実際に出た場合だけ補正する。

wetは単一workerが順番に生成するので、renderはFIFOと必要なら1hopの先読みscratchで扱う。任意順の到着を並べ替えるmap、複数モデル用scheduler、予測型overload管理、ゼロコピー共有参照カウントを増やさない。

非表示で音量メーターを読む必要はないが、fault表示のために小さな状態を1秒ごとに読む実装は許容する。既にイベント方式が動くなら維持する。どちらも音声をUIに依存させず、描画は止める。わずかなpollをゼロにするためだけに新しい通知基盤を作らない。

## 既にv2実装が進んでいる場合
通常運転できる3queue、各状態機械、C ABI、native control thread、フォーマット変換、通知方式は残す。v3の推奨部品へ改名・置換しない。主な変更は実行プロンプト、必須テスト選択、記録方式、最適化の終了条件である。既存の高速な有益テストは保存し、関連するものだけ再利用する。

## 負担削減の限界
短い確認だけでは、全機種・数時間後・スリープ組合せ・厳密な数%のゲーム影響は保証できない。これらを検証済みとは書かない。その代わり、対象機の通常利用で動くこと、NCが実際に適用されていること、要求機能がそろっていることを直接確認し、未確認の条件だけを納品書へ記す。
