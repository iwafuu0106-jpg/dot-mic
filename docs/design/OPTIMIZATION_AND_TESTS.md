# 最適化と最低限の検証

## 1. 運用の原則
指定機能を今回で完成させる。削減対象は、検証の重複、全条件の網羅、同じ条件の反復、証拠資料の形式要求である。音声・NC・UIの機能を削ってテストを減らさない。

標準の検証入口は二つだけにする。実装環境が複数エージェントを使える場合、独立したread-onlyレビューや別環境のsmokeを並列化してもよいが、同じ確認を重複実行して試験量を増やさない。

|入口|内容|実行方針|
|---|---|---|
|コア自動試験1本|小さい参照fixture、DSP、queue/NC状態、clock controller|関連実装の初回完成時に一度。変更後は影響グループだけ|
|配布版の実機確認1セッション|実音声、ON/OFF、操作感、常駐、設定保存、性能の基準測定|標準5分の確認手順にまとめ、起動smokeと最適化の計測を兼用|

「1本」は56件の試験を名前だけまとめたものではない。独立した網羅matrixを廃止し、下記の代表故障だけを短い入力で確認する。既に合格したコードを工程移動だけで再試験しない。既存の有益で高速なテストは消す必要がないが、全量実行は義務にしない。

5分は正常時の標準セッション予算であり、ビルド・環境設定・モデル取得に要する時間は含まない。問題発見時に時間が来たから合格にする意味ではない。故障した項目だけ修正・再現確認する。

## 2. コア自動試験の最小内容
共通のproduction部品を呼ぶ一つのrunnerに、次の4グループだけを用意する。テスト専用の別DSPを本実装の代わりにしない。すでに同等の試験があれば追加せず再利用する。

**モデル参照。** 使用許諾が明らかな短い一つのfixture（声・無音・雑音区間を含む）から、固定モデルと公式streaming前後処理で参照を作る。nativeの前後処理、連続state、reset後の再現、固定source alignmentを同じ実行で比較する。shape/初期normは初期化時の検査を兼ねる。FFTだけの問題を切り分けるidentity OLAを添えるが、多数の独立モデルベンチは作らない。数値許容は実データの計算差を説明して固定し、通すためだけに拡大しない。v2で同じmodel/実装の参照証拠があれば再生成不要。

**DSP。** 一つの合成シーケンスに小さいsine、閾値前後の段差、過大peak、無音、非有限入力を含める。gainの0/+6dBと20msの連続変化、gateのhysteresis/hold/release、gateOFF、最終sample ceiling、finite出力をまとめてassertする。全gain×全閾値×全sample形式の直積は回さない。gainはheadroomが十分な区間で測り、limiterで潰れた区間を倍率試験に使わない。

**受渡しとNC制御。** 短い可変packet列でsample順序・端数・ring wrapを確認し、通常ON/OFF、準備中OFF、fade途中反転を各一度通す。NC worker相当の100ms遅延を一度注入し、renderが待たず同位置のdryへ進むことを確認する。満杯によるNC job欠落と旧generationの結果を各一度扱い、同じ共通fault処理へ入ること、Off確定後にRun数が増えないことをassertする。100回トグル、50/100/500msの全組合せ、sleepとの総当たり、ランダムfuzzは標準にしない。

**clock。** productionの水位制御関数に±200ppmの入力／出力差を与え、10分相当の仮想時間を決定的に進める。実時間sleepやNC推論は回さない。補正符号、補正上限、水位が容量へ発散しないことを確認する。新規P制御の残留偏差を0にするassertは書かない。既存PIならその実装を使う。SRC自体の入出力数と端数処理は短いDSP/受渡し確認で扱い、仮想controller試験を実機の長時間安定性の証明とは呼ばない。

nativeの所有権・C ABI・capture/renderの確保／mutex／I/Oは、該当箇所のコード確認を基本とする。専用heap監視器、全APIの悪意入力試験、ORT内部の証明を作らない。実際のcrash、異常確保、音切れの原因として必要なら、その箇所だけ計測する。

## 3. 実機確認セッション
実際に渡すZIPを別フォルダーへ展開し、そのRelease版を使う。最初の一回の起動確認、機能確認、操作感、性能測定を同じセッションにする。機器はまず利用者が実際に使うmicとvirtual endpoint、現在のWindows・DPI・モニターで足りる。

最初の3区間を各60秒としてCPU等を集計する。OFF非表示、ON非表示、ON＋Full操作の順を基本とし、同じfixture／端点／gain／gate条件にする。cold model loadとNC準備中は別記し、定常ONへ混ぜない。OFF/ONの音の違いは短い発話／許諾fixtureで聴き、数字だけで音質を判定しない。

残りの短い確認でmain→hide→tray→main、ノブdrag/wheel/微調整/数値入力、gate、menu、Full/Reduced/Off、keyboard focus、設定保存後の再起動、Exitを一通り使う。current DPIで欠けや誤クリックがないことを見る。実機を操作できる場合は同じ端点の再接続を一度だけ試し、他のmic/speakerへ勝手に移らないことを確認する。

自動起動は自分のHKCU登録→読み戻し→解除を同じ確認で済ませる。サインアウト／OS再起動／Explorer強制終了は必須にしない。これらの通知ハンドラは実装するが、実際の再起動未確認はそのまま記す。必要なら通知処理の直接呼出による小さい確認で足り、専用OS操作ハーネスを作らない。

virtual captureから音が取れることは確認する。Discordが利用可能なら同じセッション内で入力を選び、短い受信確認を兼用する。利用できない場合は「仮想入力まで確認、Discord個別未確認」と分けて記す。アプリ内meterが動いたことだけを経路成立にしない。実音声を無断で保存しない。

ゲームが既に利用可能なら、再現しやすい一場面でアプリ停止とNC ONの短い比較を一組だけ行う。用意済みのfps/frame表示があれば利用し、なければ挙動と音声の継続を確認する。NC ON非表示の60秒区間と兼用してよいが、異なるゲーム負荷のCPU値を同条件のA/Bとは扱わない。anti-cheatに介入するhookや専用ゲーム自動化は作らない。ゲーム不在を理由に複数タイトルの調達・網羅測定を始めない。

実行できない確認は「未確認」であり、PASSにはしない。ただし動画や精密frame計測の欠如を、全製品の完成停止要因にしない。長い未実行チェックリストを納品条件として利用者へ丸投げせず、未確認の範囲だけ短くまとめる。

## 4. E4：最適化は必須、無意味な改造は不要
最適化の基準計測は必須とする。最終候補buildで上の3区間を実施し、十分であればそのセッションをE5の実機確認にも使う。機能が未完成のmockをbaselineにしない。

通常保存する数値は、process CPU秒/実秒で求めたcore-equivalent、NC hop全体の平均/p99、Run回数、NC要求区間のwet採用率、fallback/xrun件数、private bytes、代表的なdry水位だけ。機器、OS、model hash、build、fixture、区間の条件を一つのCSV冒頭等に記録する。hopごとの大量JSONや全sampleログを常設しない。

NC時間はSTFT・Run・ISTFTを含む全体を測る。開始前に確保したtiming bufferへ記録し、集計は音声thread外で行う。必要になるまで演算子別の時刻、context switch、page fault、p99.9、ETW収集を増やさない。停止したNCや原音fallbackを正常なON性能として数えない。

以下は改善の目安であり実測済みの数値ではない。目安を満たすための総当たりや微差の統計検定は不要。

|目安|使い方|
|---|---|
|NC平均hop処理 < 10ms、p99は6ms以下を目標|平均で追従不能・持続的なwet欠落は直す。p99目安を単独の全機種保証にしない|
|NC ON非表示CPU ≤ 0.35 core-equivalent|1論理coreの35%相当。対象CPUの実測と実NC適用を併記|
|NC OFF非表示CPU ≤ 0.02 core-equivalent|Runが止まっていることがまず必須。1Hzの状態pollは許容|
|Full追加CPU ≤ 0.20 core-equivalent|2026-10-06 UI刷新のユーザー指定で従来0.10の2倍。同じ条件で非表示との差|
|private bytes ≤ 500MiB|UI刷新の予算は従来250MiBの2倍。明らかな増え続ける挙動や重複sessionを優先して直す|
|追加経路遅延は100ms以下を設計目標|共通delay/queue/device情報を記録。実全経路を測れていないなら推定と明記|
|Fullは60fps相当の滑らかさを目標|実操作で引っかかりを確認。実presentを測らず60fps達成と数値宣言しない|

v2のゲームp99+3%以内、p99.9<10ms、全条件3run、全項目heap traceは標準から外す。精密な全経路遅延測定器やpresent計測器を新規開発しない。すでに使える診断があれば利用する。遅延が不自然に大きい、描画が止まる等の具体的問題が出たときだけ掘り下げる。

## 5. 改善の順番と終了条件
最初にコードの明白な無駄を見る。hopごとのOrtValue/state/FFT確保やcopy、入力48kなのに毎回SRC、sampleごとのpow/log、全ボタンtimer、非表示描画／meter、空poll、同じsessionの重複を優先する。必要な整合delayと独立dryは維持する。

明白な無駄を直しても予算外なら、最も大きい箇所だけ短くprofileする。既定と有望候補の二つを比較し、通常は各60秒一回で足りる。graph level、arena、I/O Binding、period、reserve、ISAの直積探索は禁止。thread=1、CPU、モデル、FP32、48k/480hop、Fullは変えない。

有益な差が明らかなら採用し、関連するコアグループまたは操作だけを再確認する。差が揺らぐ・小さいなら優劣を断定せず単純な方へ戻す。僅差の順位決めのためだけに3回、5回と追加しない。目標内で無駄も見当たらなければ、変更ゼロで最適化工程を終了してよい。

最適化後の全機能動画、全自動suite、30分soakの再実行は不要。E4で何も変更していなければbefore/afterを別々に測らず「変更なし、基準測定のみ」と報告する。工程を完了するために棄却案やボトルネックを捏造しない。

E4の終了時に、基準測定と必要な修正を通過したRelease candidateをfreezeする。最低限、実行バイナリ一式のhash、モデルSHA-256、source commit/tree hash、Release設定を記録する。E5のpackageはこの同一RCを使用する。freeze後にproduction code/model/dependency/build flagsを変更した場合だけ新RCとして影響確認へ戻し、文書・ライセンス表記・ZIP内説明だけの変更では音声／性能測定を繰り返さない。

## 6. 再テストを増やしてよい条件
追加するのは、再現した不具合、コードから具体的に見つかった欠陥、変更した重要経路を既存の確認で覆えない場合だけ。WORKLOGへ「どの故障を／どの差分のために／既存のどの確認では足りないか」を一行記して、最小のケースを追加する。根拠のない念のため、全matrix、カバレッジ目標、回数達成のための追加は禁止。

|変更|再確認|
|---|---|
|文章・色・余白|変更画面を見るだけ。音声試験なし|
|ノブ／toggle／popup動作|その操作を一度。音声計算を触っていなければモデル参照不要|
|NC前後処理・state・graph|モデル参照グループ＋変更箇所の短い聴感確認|
|queue・NC停止・clock・lifetime|対応コアグループ＋短い実経路確認。30分へ自動拡張しない|
|依存・配布構成|ZIP展開起動＋影響機能。buildが同じなら全音質測定なし|

不具合があるのに試験回数上限を理由に放置しない。長い試験を繰り返す代わりに、短く再現するケースへ縮めて修正する。変更していない証拠は再利用する。

## 7. 完成の扱い
完成確認は、要求機能がそろい、選択したモデルが正しく動き、NC OFFで演算が止まり、対象経路で音が届き、UI／常駐が実操作でき、重大な再現不具合がなく、配布物が起動することで判断する。単なる設計書、見た目だけのmock、NC常時fallbackでは完了しない。

音質・ゲーム影響・長時間互換性は確認範囲を明記する。短い1回の実行は統計的な信頼性保証ではない。ここでは工程負荷を抑えて主要な実装ミスを検出する選択である。実測しなかった条件を隠さず、全条件の未検証を一括の無限検証ゲートにもしない。
